Kafka
=====
cluster = multiple brokers
broker = server
purpose of broker is to serve data
each broker in a cluster is also a bootstrap server
3 brokers is usual
kafka broker discovery. uses metadata in servers
consumer = client
data stored in topics
topics are persisted on disk

Producer
--------
A Kafka producer is a client or application that sends (publishes) messages to Kafka topics.
It connects to a Kafka broker (a Kafka server node).
It specifies a topic (like order.created or payment.processed).
Kafka decides which partition in that topic to write the message to.
The message is stored durably in Kafka — ready for consumers to read.
If you call .emit() → you’re a Kafka Producer


Consumer
--------
A Kafka consumer → listens for messages from Kafka (reads from a topic)
A consumer subscribed to "order.created" receives the message.
The consumer processes it (for example: send an email, charge payment, update DB).
If you use @MessagePattern() → you’re a Kafka Consumer


Client
------
A Kafka client is any application or library that communicates with a Kafka cluster, either to:
Produce messages (send/publish to topics)
Consume messages (read/subscribe from topics)
The “client” is the umbrella term for anyone interacting with Kafka.


why are the producer and consumer created in different ways
-----------------------------------------------------------
Microservice (Consumer)
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
  transport: Transport.KAFKA,
  options: {
    client: { clientId: 'payments', brokers: ['kafka:9092'] },
    consumer: { groupId: 'payments-consumer' },
  },
});


NestJS creates a Kafka microservice instance.
This is primarily for consuming messages (Kafka consumer).
NestJS automatically maps message patterns (from @MessagePattern()) to your handlers.
NestJS internally manages the Kafka consumer lifecycle, including connecting, subscribing to topics, handling retries, and listening.
So the microservice is “consumer-centric”: its main job is to receive messages, not to send them.



Kafka Client (Producer)
ClientsModule.register([
  {
    name: 'PAYMENTS_PRODUCER',
    transport: Transport.KAFKA,
    options: {
      client: { clientId: 'payments-producer', brokers: ['kafka:9092'] },
      producer: {},
    },
  },
]);


This creates a standalone Kafka client.
Its main purpose is to send messages to Kafka topics (emit or send).
It does not automatically subscribe to topics — it only produces messages.
You have to inject it into a service and call .connect() manually (or via OnModuleInit) before sending messages.


NestJS separates these roles because Kafka producers and consumers have different responsibilities:

| Aspect               | Microservice (Consumer)                           | ClientKafka (Producer)                |
| -------------------- | ------------------------------------------------- | ------------------------------------- |
| Primary role         | Receive messages                                  | Send messages                         |
| Lifecycle management | Automatic with `NestFactory.createMicroservice`   | You manage `.connect()`               |
| Message handling     | `@MessagePattern()`                               | `.emit()` / `.send()`                 |
| Multiple instances   | Each microservice can have its own consumer group | Multiple producers can share a broker |



Why they’re “different ways”
Consumer: You need a NestJS microservice, because consuming involves automatically handling topics, partitions, groups, and lifecycle.
Producer: Sending messages is simpler — you just need a Kafka client that knows the broker info. You don’t need the full microservice machinery for that.


NestJS essentially gives you two abstractions:
Microservice → for consumers
ClientKafka → for producers


NestJS terminology

NestFactory.createMicroservice → creates a microservice that is primarily a consumer. It automatically listens to Kafka topics and routes messages to handlers.
ClientKafka → creates a client object that allows you to produce messages (emit/send) to Kafka.
Even though the class is called ClientKafka, in practice:
It is producer-focused.
You can technically use it in request-response patterns, where it also consumes a reply, but it doesn’t subscribe to arbitrary topics like a “real” consumer does.

NestJS separates them because the lifecycle and responsibilities of producers and consumers are different:
| NestJS Concept | Kafka Concept | Responsibility                                                                            |
| -------------- | ------------- | ----------------------------------------------------------------------------------------- |
| Microservice   | Consumer      | Subscribes, receives messages, handles partitions, manages offsets automatically          |
| ClientKafka    | Producer      | Sends messages, optionally waits for a reply, does not manage subscriptions automatically |


Key takeaway
The name is misleading, but the behavior is intentional: ClientKafka is producer-centric, even though technically Kafka producers are also “clients.”
If you need a true consumer, NestJS expects you to use a microservice (or manually create a KafkaJS consumer outside NestJS abstractions).
In short: NestJS treats producers and consumers differently, so the naming doesn’t fully align with Kafka semantics.


=============================================
KafkaJS vs NestJS: What’s the difference?

KafkaJS is a low-level client library for interacting with Kafka directly (producers, consumers, etc.).

NestJS is a framework that provides higher-level abstractions — including one built on top of KafkaJS (or other transport layers).

In NestJS, the Kafka integration is part of its microservices module, which provides two main roles:

Role	KafkaJS equivalent	NestJS abstraction	Purpose
Producer	kafka.producer()	ClientKafka	Send messages/events
Consumer	kafka.consumer()	@MessagePattern() handler in a @Controller() with a Microservice	Receive messages

So — yes — while in KafkaJS you create both the producer and consumer from the same Kafka instance, in NestJS these are split into two separate mechanisms, because NestJS handles the consumer lifecycle internally in the microservice layer.

⚙️ 2. How NestJS sets this up
Producer side (using ClientKafka)

In your app module or service:

import { ClientKafka, ClientsModule, Transport } from '@nestjs/microservices';

@Module({
  imports: [
    ClientsModule.register([
      {
        name: 'KAFKA_SERVICE',
        transport: Transport.KAFKA,
        options: {
          client: {
            clientId: 'my-producer',
            brokers: ['localhost:9092'],
          },
          consumer: {
            groupId: 'my-producer-group', // still needed internally
          },
        },
      },
    ]),
  ],
})
export class AppModule {}


Then inject and use it:

@Injectable()
export class AppService {
  constructor(@Inject('KAFKA_SERVICE') private kafkaClient: ClientKafka) {}

  async onModuleInit() {
    await this.kafkaClient.connect();
  }

  sendMessage() {
    this.kafkaClient.emit('test-topic', { value: 'Hello from producer!' });
  }
}

Consumer side (using Microservice)

In your main.ts (for a microservice instance):

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
import { Transport } from '@nestjs/microservices';

async function bootstrap() {
  const app = await NestFactory.createMicroservice(AppModule, {
    transport: Transport.KAFKA,
    options: {
      client: {
        clientId: 'my-consumer',
        brokers: ['localhost:9092'],
      },
      consumer: {
        groupId: 'test-group',
      },
    },
  });

  await app.listen();
}
bootstrap();


And your consumer logic lives in a controller:

import { Controller } from '@nestjs/common';
import { MessagePattern, Payload } from '@nestjs/microservices';

@Controller()
export class AppController {
  @MessagePattern('test-topic')
  consume(@Payload() message: any) {
    console.log('Received message:', message.value);
  }
}

🧠 3. So what’s happening conceptually

KafkaJS: You explicitly create both producer and consumer manually.

NestJS:

A microservice instance handles consuming.

A ClientKafka instance handles producing.

Each has its own lifecycle and connection pool, managed by NestJS.

Even though both under the hood use KafkaJS, NestJS separates them for clarity, scalability, and lifecycle management (especially across distributed services).

🔸 TL;DR
Concept	KafkaJS	NestJS
How you make a producer	kafka.producer()	ClientKafka
How you make a consumer	kafka.consumer()	Microservice + @MessagePattern()
Connection management	Manual	Managed by NestJS
Factory object	new Kafka()	Handled internally by NestJS

consumer and producer lifecycles
--------------------------------
just means how those clients are created, connected, used, and shut down over the life of your app.

The “lifecycle” of a Kafka client

Every Kafka producer and consumer goes through these phases:


| Phase                       | Description                                                                      | Example                                                       |
| --------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **Creation**                | You create a client instance (via KafkaJS or NestJS abstraction).                | `const producer = kafka.producer()`                           |
| **Connection**              | It opens one or more network connections to Kafka brokers and joins the cluster. | `await producer.connect()`                                    |
| **Usage**                   | It does its main job — send or consume messages.                                 | `await producer.send(...)` / `await consumer.run(...)`        |
| **Disconnection / Cleanup** | It gracefully closes sockets, commits offsets, leaves consumer groups, etc.      | `await producer.disconnect()` / `await consumer.disconnect()` |

Those four phases make up the client lifecycle.
If you skip or mismanage one, you’ll get resource leaks, uncommitted offsets, or lost messages.


Producer lifecycle explained
----------------------------
const producer = kafka.producer();

await producer.connect();  // ⬅️ connects to brokers

await producer.send({
  topic: 'my-topic',
  messages: [{ value: 'Hello Kafka!' }],
});

await producer.disconnect();  // ⬅️ flushes and closes connections

Key lifecycle behaviors:

connect() establishes socket connections to Kafka brokers and fetches metadata.

You must connect before sending messages.

disconnect() gracefully closes connections and ensures in-flight messages are sent.

Repeatedly connecting/disconnecting is expensive — usually, you connect once on startup and disconnect on shutdown.

In a NestJS app, that typically means:
Connect the producer in onModuleInit() or AppService.onApplicationBootstrap().
Disconnect in onModuleDestroy() or beforeApplicationShutdown().


Consumer lifecycle explained
----------------------------
const consumer = kafka.consumer({ groupId: 'my-group' });

await consumer.connect();                     // join consumer group
await consumer.subscribe({ topic: 'my-topic' });
await consumer.run({ eachMessage: async (...) => { ... } });
// ⬆️ this keeps running until you disconnect

await consumer.disconnect();  // leaves group, commits offsets, closes sockets


Key lifecycle behaviors:

connect() registers the consumer in a consumer group.

run() starts an infinite event loop — it keeps fetching messages.

You typically never “await” run(), because it keeps running forever.

disconnect() stops the loop, commits final offsets, and leaves the group.

So, in a NestJS service:

Start your consumer in onModuleInit().

Don’t block — just launch run() and handle messages asynchronously.

Clean up in onModuleDestroy().


Why lifecycles matter in NestJS


| Nest Hook                                           | When It Runs                 | Good For                                         |
| --------------------------------------------------- | ---------------------------- | ------------------------------------------------ |
| `onModuleInit()`                                    | When a module is initialized | `producer.connect()`, `consumer.connect()`       |
| `onApplicationBootstrap()`                          | After all modules are ready  | `consumer.run()`                                 |
| `onModuleDestroy()` / `beforeApplicationShutdown()` | On shutdown                  | `producer.disconnect()`, `consumer.disconnect()` |


Using these ensures:
Your Kafka connections open only once (not per request).
Your consumers and producers shut down cleanly when the app stops.
No dangling connections or locked consumer group sessions.


App startup
 ├── create Kafka clients
 ├── producer.connect()
 ├── consumer.connect()
 └── consumer.run() → (infinite loop)

App running
 ├── producer.send() (on demand)
 └── consumer processes messages continuously

App shutdown
 ├── consumer.disconnect()
 └── producer.disconnect()

TL;DR

Producer lifecycle

Connect → Send → Disconnect
(usually connect once, send many times, disconnect once)

Consumer lifecycle

Connect → Subscribe → Run (infinite loop) → Disconnect

In NestJS, you map those to the application’s own lifecycle hooks so Kafka connections open and close with the app itself — not per request.


=============================================
You only need a Producer module (ClientKafka) because:

The producer is an injectable client you use in your app to send messages.

The consumer, on the other hand, is the NestJS microservice itself — created by NestFactory.createMicroservice() or app.connectMicroservice() — not a simple injectable class.

So:

✅ Producers → live inside modules as injectable clients
🧠 Consumers → live at the application level (as a Nest microservice)



Producers vs. Consumers in NestJS architecture
| Concept      | Typical Implementation                                                  | Managed By                                              |
| ------------ | ----------------------------------------------------------------------- | ------------------------------------------------------- |
| **Producer** | `ClientKafka` inside an app module (via `ClientsModule.register`)       | Your app logic (you call `emit()` or `send()`)          |
| **Consumer** | Entire **microservice instance** created by Nest (`createMicroservice`) | NestJS framework (handles connect, subscribe, run loop) |



A producer is a component (you create one per module or service that needs to send events).
A consumer is a runtime environment (the whole process that listens to Kafka topics).

Why the difference exists

🔸 Producer (ClientKafka)
ClientKafka is designed to be:
Injected into your services
Used imperatively (emit() / send())
Controlled by your application’s lifecycle
So it fits naturally into a Nest module, just like any other dependency:

You inject and use it in a service:
constructor(@Inject('KAFKA_SERVICE') private kafka: ClientKafka) {}


Consumer (Nest microservice)
Consumers are not injected — they host message handlers (@MessagePattern) and run their own connection loop.
That’s why you don’t build a “consumer module”; instead, you start a microservice:

The consumer logic lives inside controllers:

+----------------------+          +-----------------------------+
|   Producer Module    |          |     Consumer Microservice   |
|----------------------|          |-----------------------------|
|  @Inject(ClientKafka)|          |  @MessagePattern('topic')   |
|  kafka.emit('topic') |   --->   |  handleMessage(payload)     |
|                      |          |  auto-managed by Nest       |
+----------------------+          +-----------------------------+


Mental model:

KafkaProducerModule = just a helper module that gives your app a producer client.

Kafka consuming is not a module at all — it’s an app runtime role that NestJS takes over.

kafka - process message once only

Ensuring a Kafka message is processed exactly once is one of the trickiest and most important aspects of building robust Kafka applications. Let’s go carefully step by step.

1️⃣ Understand Kafka’s Delivery Semantics

Kafka itself provides at-least-once delivery by default:

At-least-once: Consumers may see a message multiple times if they fail before committing offsets.

At-most-once: Messages may be lost if offsets are committed before processing.

Exactly-once: A combination of idempotent writes, transactions, and offset management ensures each message affects your system only once.

2️⃣ Use Idempotent Producers

If a producer retries sending a message due to a network failure, you don’t want duplicates. Kafka supports idempotent producers:

const { Kafka } = require('kafkajs');
const kafka = new Kafka({ brokers: ['localhost:9092'] });

const producer = kafka.producer({ idempotent: true });
await producer.connect();
await producer.send({
  topic: 'my-topic',
  messages: [{ key: '1', value: 'hello' }],
});


✅ Ensures the same message isn’t written twice even if the producer retries.

3️⃣ Transactions for Atomic Processing

If you want end-to-end exactly-once (message consumed, processed, and written to another topic or DB):

Enable transactions in the producer:

const producer = kafka.producer({
  idempotent: true,
  transactionalId: 'my-transactional-id',
});
await producer.connect();


Wrap your processing and offset commit in a transaction:

const transaction = await producer.transaction();

try {
  // Send processed message to output topic
  await transaction.send({
    topic: 'output-topic',
    messages: [{ key: '1', value: 'processed' }],
  });

  // Commit consumer offsets as part of the same transaction
  await transaction.sendOffsets({ 
    consumerGroupId: 'my-group',
    topics: [{ topic: 'input-topic', partition: 0, offset: '5' }],
  });

  await transaction.commit();
} catch (err) {
  await transaction.abort();
}


✅ Guarantees atomicity: either both the output message and offset commit happen, or neither.

4️⃣ Manual Offset Management (if not using transactions)

If you don’t use transactions:

Disable auto-commit: enable.auto.commit = false

Only commit offsets after successful processing:

for await (const message of consumer) {
  await process(message);       // your processing logic
  await consumer.commitOffsets([
    { topic: 'input-topic', partition: message.partition, offset: message.offset + 1 }
  ]);
}


⚠️ Risk: If your processing fails after committing, messages can be lost. Transactions eliminate this risk.

5️⃣ Idempotent Processing on the Consumer Side

Even with at-least-once delivery, you can make your system effectively exactly-once by making your processing idempotent:

Assign a unique key or ID to each message.

Store processed IDs in a database.

Skip any message whose ID is already processed.

Example (pseudo-code):

if (!db.hasProcessed(message.key)) {
  db.saveProcessed(message.key);
  doProcessing(message.value);
} else {
  // Skip duplicate
}


This ensures duplicates have no effect.

6️⃣ Kafka Streams Option

If you use Kafka Streams:

Set processing.guarantee = exactly_once_v2

Streams handles:

Idempotent writes

Transactional offset commits

State management

You get true exactly-once semantics between input and output topics automatically.

✅ Summary
Layer	How to Ensure Exactly Once
Producer	idempotent=true + retries
Consumer	Manual offset commit after processing
Processing	Make operations idempotent
Cross-topic	Use Kafka transactions
Stream processing	Use Kafka Streams exactly-once mode

Orders Service – Kafka Producer

apps/orders/src/main.ts

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
import { Transport, MicroserviceOptions } from '@nestjs/microservices';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // Create a Kafka microservice client
  app.connectMicroservice<MicroserviceOptions>({
    transport: Transport.KAFKA,
    options: {
      client: {
        brokers: ['kafka:9092'], // Docker network hostname
      },
      producerOnlyMode: true,
    },
  });

  await app.startAllMicroservices();
  await app.listen(3001);
  console.log('Orders service running on http://localhost:3001');
}
bootstrap();


orders.service.ts

import { Injectable } from '@nestjs/common';
import { CreateOrderDto } from '@app/common';
import { ClientKafka } from '@nestjs/microservices';
import { Inject } from '@nestjs/common';

@Injectable()
export class OrdersService {
  constructor(
    @Inject('ORDERS_SERVICE') private readonly kafkaClient: ClientKafka
  ) {}

Do Microservices Share a Single Database?

No — they shouldn’t.

Each microservice should have its own database, which only it owns and manages.

✅ Correct approach:
+------------------+         +-------------------+
| Orders Service   |         | Payments Service  |
| MongoDB (orders) |         | MongoDB (payments)|
+------------------+         +-------------------+


Each service:

Owns its data schema

Manages its migrations

Can choose its own database technology (e.g., MongoDB, Postgres, Redis, etc.)

Exposes data to other services only via APIs or messages (Kafka, RabbitMQ, etc.)

❌ Anti-pattern (shared database):
           +-----------------------------+
           |     Shared database         |
           |  orders, payments, users... |
           +-----------------------------+
              ↑               ↑
      Orders Service   Payments Service


This violates service boundaries and couples services together:

Changing one schema may break another service

Harder to scale independently

Violates “independent deployability,” one of the key goals of microservices








Does the Database Run as a Microservice?

Not really.
A database is a dependency, not a microservice.

Microservices are independent deployable applications with business logic, APIs, and message handling.
A database is just a stateful resource that supports one of those services.

Example:

Your docker-compose.yml might look like this:

services:
  orders:
    build: ./orders
    ports:
      - "3001:3001"
    depends_on:
      - orders-db

  payments:
    build: ./payments
    ports:
      - "3002:3002"
    depends_on:
      - payments-db

  orders-db:
    image: mongo
    ports:
      - "27017:27017"

  payments-db:
    image: mongo
    ports:
      - "27018:27017"


Here:

orders-db and payments-db are containers (infrastructure services),
not microservices.

They don’t contain application logic — they just persist data.

💡 3️⃣ How Services Share or Query Each Other’s Data

Since they can’t query each other’s databases directly, they communicate using:

HTTP APIs (REST or GraphQL)

Event streams (Kafka, RabbitMQ, NATS)

gRPC (binary RPC communication)

Example (event-driven):

Orders Service → [orders.created] → Kafka → Payments Service


Payments learns about new orders by consuming the event,
not by querying the Orders database.

🧠 Summary
Question	Answer
Do microservices share a single DB?	❌ No — each has its own.
Is a DB a microservice?	❌ No — it’s a data store, not an independent service.
How do they share data?	✅ Through APIs or events, never direct DB access.
Benefit	✅ Loose coupling, independent scaling & deployment.




Ways to Handle Lost Updates

1️⃣ Database-Level Concurrency Control
a. Transactions with Isolation Levels

If you use SQL databases, you can use transaction isolation levels such as:

REPEATABLE READ

SERIALIZABLE

Example (PostgreSQL / MySQL):

BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT balance FROM accounts WHERE id = 1; -- returns 100
UPDATE accounts SET balance = balance + 10 WHERE id = 1;

COMMIT;


If another transaction tries to modify the same row concurrently, the database will:

block it, or

throw a serialization error that you can retry.

🧠 NestJS can handle this by using TypeORM or Prisma with transaction blocks.

b. Optimistic Concurrency Control (OCC)

This is the most microservice-friendly approach because it avoids DB-level locks.

You add a version field (or timestamp) to your record.

Example:

interface Account {
  id: number;
  balance: number;
  version: number;
}


Flow:

Service A reads account (balance=100, version=1)

Service B reads account (balance=100, version=1)

Service A updates → sends {balance:110, version:1}

DB checks: is current version still 1?

✅ yes → update and increment to 2

Service B updates → sends {balance:95, version:1}

❌ version mismatch → reject (lost update prevented)

SQL example:

UPDATE accounts
SET balance = 95, version = version + 1
WHERE id = 1 AND version = 1;


If rows affected = 0, it means someone else updated it first — you can then re-read and retry.



2️⃣ Application-Level Coordination
If multiple microservices work on the same data model, you can coordinate updates:

Use a message broker (Kafka, RabbitMQ) and funnel all updates for a record through a single consumer.

That consumer ensures serial processing of events per entity key (e.g., one account ID at a time).

Kafka, for instance, guarantees message order within a partition → this can effectively serialize updates.


Distributed Locking (Advanced)
Sometimes you can’t avoid concurrent writes, and you need an external lock manager.

Use Redis Redlock, etcd, or Zookeeper to acquire a lock before modifying data.

Lock lifetime is short (e.g., a few seconds).

Only one service can hold the lock for a given resource.

Example (using Redis):

const lock = await redlock.acquire(['lock:account:1'], 2000);
try {
  // safely modify account 1
} finally {
  await lock.release();
}


This prevents concurrent modifications across service instances.



4️⃣ Domain-Driven Design (Data Ownership)

At a higher architectural level, microservices should not normally share write access to the same data.

Instead:

Each service owns its own data (own DB).

Other services communicate via events (e.g., OrderPlaced, UserBalanceUpdated).

This avoids race conditions entirely, since no two services are updating the same record directly.

If another service needs that data, it keeps a read replica (eventual consistency).


Summary
Strategy								      Layer					      Prevents Lost Update					Notes
DB transactions							  Database			    	✅ Yes									      Simplest for monoliths or small microservices
Optimistic concurrency				Application			  	✅ Yes									      Ideal for stateless microservices
Distributed locking						Infrastructure			✅ Yes									      Adds complexity, use when needed
Event-driven design						Architecture		  	✅ By design							    Best long-term strategy

So instead of guessing folder locations, Nest knows exactly where the project lives and how to compile it.

🔹 TL;DR

nest-cli.json is Nest CLI configuration.

It tells Nest:

Where source code lives (sourceRoot)

How to compile the app (compilerOptions)

Project names and locations in monorepos (projects)

Nest CLI commands read this file to know how to build/run/generate files.


Nest CLI uses nest-cli.json to locate TypeScript configs

When you run a command like:

nest build


Nest CLI:

Reads nest-cli.json at the root of the project.

Determines which project to build:

If no project is specified: builds the “default” root project.

If --project <name> is specified: builds that project.

Reads the tsConfigPath under the project in nest-cli.json to find the TypeScript configuration file (usually tsconfig.app.json).

Example

Your nest-cli.json in the monorepo has:

"projects": {
  "gateway": {
    "type": "application",
    "root": "apps/gateway",
    "sourceRoot": "apps/gateway/src",
    "compilerOptions": {
      "tsConfigPath": "apps/gateway/tsconfig.app.json"
    }
  }
}


gateway → project name

root → folder for source files

tsConfigPath → exact path to TypeScript configuration

When you run:

nest build gateway


Nest CLI uses apps/gateway/tsconfig.app.json to compile the project.
✅ If you run nest build without specifying the project, it defaults to the root project defined in nest-cli.json (apps/my-nestjs-monorepo-app in your case). That’s why Docker kept failing — it tried to find apps/my-nestjs-monorepo-app/tsconfig.app.json instead of apps/gateway/tsconfig.app.json.

Dockerfile set:

RUN npm run build


npm run build runs the script from root package.json, which internally calls nest build.

Nest CLI sees no project specified, so it tries to build the root project (apps/my-nestjs-monorepo-app).

Inside the container, that folder exists, but the tsconfig.app.json path it looks for is wrong, causing:



4. Summary

nest-cli.json defines your monorepo’s projects and TS configs.

  Use HTTP Proxy (for HTTP microservices)
If your microservices expose HTTP REST APIs, you can proxy requests instead
A popular solution: http-proxy-middleware
npm install http-proxy-middleware

// main.ts
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
import { createProxyMiddleware } from 'http-proxy-middleware';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // Forward /users/* requests to User Service
  app.use(
    '/users',
    createProxyMiddleware({
      target: 'http://localhost:3001',
      changeOrigin: true,
      pathRewrite: { '^/users': '' },
    }),
  );

  // Forward /orders/* requests to Orders Service
  app.use(
    '/orders',
    createProxyMiddleware({
      target: 'http://localhost:3002',
      changeOrigin: true,
      pathRewrite: { '^/orders': '' },
    }),
  );

  await app.listen(3000);
}
bootstrap();
