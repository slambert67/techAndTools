Logging
-------
Logger class in @nestjs/common
Customize passing object during app creation in main.ts - const app = await NestFactory.create(AppModule, {});
	logger: false
	logger: ['log', 'fatal', 'error', 'warn', 'debug', 'verbose']

alternative:
const app = await NestFactory.create(AppModule, {
  logger: new ConsoleLogger({
    colors: false,
  }),
});

Because nestjs has a pluggable logging system

logger: false					configures Nest's internal logger setup
								Nest automatically instantiates it's own ConsoleLogger
						
logger: new ConsoleLogger		injecting own logging instance
								can be subclassed or replaced entirely. see WinstonLogger, PinoLogger
								
services can use logging in 2 ways
	built in static logger that uses Logger class
	
		Nest creates a default ConsoleLogger internally.
		The service uses Logger, which automatically delegates to that default logger.
		
		import { Logger } from '@nestjs/common';
		private readonly logger = new Logger(AppService.name);				manual creation. Still delegates to Nest's shared global logger configured via NestFactory
		this.logger.log('Hello called');
	
	
	custom injected logger instance	that implements LoggerService
		
		import { ConsoleLogger } from '@nestjs/common';
		constructor(private readonly logger: ConsoleLogger) {}				dependency injection. Can register globally or per module
		this.logger.log('Custom log from MyLogger');


Why You Might Want a Unique (Transient) Logger Instance

1. Automatic Context Isolation
	If you give each module or service its own instance, that logger can automatically set and remember its context (the class/module name).
	ConsoleLogger.setContext
	
2. Module-level configuration
	Each instance can hold metadata or configuration specific to its module or service.
	
3. Better Debugging and Tracing
	With transient loggers, you can easily inject a new one for a specific request, job, or module

Jest Testing
============
import { Test, TestingModule } from '@nestjs/testing';
	provides helpers to build a NestJS application context for testing
	
import { AppController } from './app.controller';
	the controller we're testing
	
import { AppService } from './app.service';
	the service dependency used by the controller
	
Jest’s describe groups related tests.
beforeEach runs before every test in the describe

Test.createTestingModule({...})
	Creates a temporary NestJS module for testing purposes.
	
.compile()
	Builds (compiles) the testing module → Nest does DI (dependency injection), wiring everything up just like in a real app. No mocking
	
app.get<AppController>(AppController)
	Retrieves an instance of AppController from the testing container
	This is now a fully functional controller, with its AppService dependency injected

| #        | Factor                  | What it means                                                      | NestJS / Microservices example                                                                 |
| -------- | ----------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| **I**    | **Codebase**            | One codebase tracked in version control, many deploys.             | A single Git repo for your service; multiple deployments (dev, staging, prod).                 |
| **II**   | **Dependencies**        | Declare and isolate dependencies explicitly.                       | Use `package.json` and avoid global packages; rely on Docker layers.                           |
| **III**  | **Config**              | Store configuration in the environment, not in code.               | Use `@nestjs/config` or environment variables instead of hardcoding secrets.                   |
| **IV**   | **Backing Services**    | Treat backing services (DB, queues, caches) as attached resources. | Your PostgreSQL, Redis, or RabbitMQ URLs should be configurable, not hardcoded.                |
| **V**    | **Build, Release, Run** | Strictly separate build, release, and run stages.                  | Use CI/CD to build Docker images (build), tag them (release), and run containers.              |
| **VI**   | **Processes**           | Execute the app as one or more stateless processes.                | NestJS apps should be stateless; store session/state in Redis or DB.                           |
| **VII**  | **Port Binding**        | Export services via port binding, not via web server injection.    | A NestJS app listens on its own port (`app.listen(PORT)`); no need for Apache/nginx embedding. |
| **VIII** | **Concurrency**         | Scale out via the process model.                                   | Run multiple instances of your microservice behind a load balancer.                            |
| **IX**   | **Disposability**       | Fast startup and graceful shutdown.                                | NestJS apps handle SIGTERM to close DB connections cleanly; Docker containers stop quickly.    |
| **X**    | **Dev/Prod Parity**     | Keep development, staging, and production as similar as possible.  | Use Docker Compose locally and Docker/Kubernetes in prod with same envs.                       |
| **XI**   | **Logs**                | Treat logs as event streams.                                       | Write logs to stdout/stderr; let the platform (Docker/K8s) aggregate them.                     |
| **XII**  | **Admin Processes**     | Run admin/management tasks as one-off processes.                   | Migrations or data imports should be run as separate scripts, not baked into app startup.      |
