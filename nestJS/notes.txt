Path parameters (a.k.a. route parameters)
  Part of the URL path itself
  Used to identify a specific resource
  eg. GET /users/123/orders/45
    123 is the userId, 45 is the orderId
  
  NestJS
  @Get('users/:userId/orders/:orderId')
  getOrder(@Param('userId') userId: string, @Param('orderId') orderId: string) {
    return { userId, orderId };
  }


Query parameters
  Appended to the URL after a ?
  Used for filtering, searching, sorting, pagination, etc
  eg. GET /products?category=books&sort=price&limit=10

  NestJS
  @Get('products')
    findProducts(@Query('category') category: string, @Query('sort') sort: string, , @Query('limit') limit: number) {
    return { category, sort, limit };
  }


  Header parameters
    Sent in the HTTP headers.
    Commonly used for authentication, content type, API keys, metadata.

    GET /profile
    Authorization: Bearer <token>
    Content-Type: application/json

    @Get('profile')
    getProfile(@Headers('authorization') authHeader: string) {
      return authHeader;
    }



  Body parameters
    Sent in the request body (not the URL)
    Used mainly in POST, PUT, PATCH requests when sending data

    POST /users
    Content-Type: application/json

    {
      "username": "alice",
      "email": "alice@example.com"
    }

    @Post('users')
    createUser(@Body() body: { username: string; email: string }) {
      return body;
    } 

  
  Cookie parameters
    Sent in the Cookie header.
    Often used for session IDs or authentication tokens

    GET /dashboard
    Cookie: sessionId=abcd1234; theme=dark

  @Get('dashboard')
  getDashboard(@Cookies('sessionId') sessionId: string) {
    return sessionId;
  }

Exception filters
-----------------
Exception Layer

	global exception filter
		Handles exceptions not handled by application
		handles exceptions of type HttpException (and subclasses of it)
		if unrecognized
			{
			  "statusCode": 500,
			  "message": "Internal server error"
			}	

		partially supports the http-errors library
		Basically, any thrown exception containing the statusCode and message properties will be properly populated and sent back as a response
		
		HttpStatus. This is a helper enum imported from the @nestjs/common package.
		throw new HttpException('Forbidden', HttpStatus.FORBIDDEN);
		
		The HttpException constructor takes two required arguments which determine the response:
			The response argument defines the JSON response body. It can be a string or an object as described below.
			The status argument defines the HTTP status code.

		By default, the JSON response body contains two properties:
			statusCode: defaults to the HTTP status code provided in the status argument
			message: a short description of the HTTP error based on the status
			
		
		BUILT-IN Exceptions aren't logged - part of normal application flow
		Can write custom exceptions
		
	Exception Filters
		Give full control
		eg. add logging
		
		

Logging
-------
Logger class in @nestjs/common
Customize passing object during app creation in main.ts - const app = await NestFactory.create(AppModule, {});
	logger: false
	logger: ['log', 'fatal', 'error', 'warn', 'debug', 'verbose']

alternative:
const app = await NestFactory.create(AppModule, {
  logger: new ConsoleLogger({
    colors: false,
  }),
});

Because nestjs has a pluggable logging system

logger: false					configures Nest's internal logger setup
								Nest automatically instantiates it's own ConsoleLogger
						
logger: new ConsoleLogger		injecting own logging instance
								can be subclassed or replaced entirely. see WinstonLogger, PinoLogger
								
services can use logging in 2 ways
	built in static logger that uses Logger class
	
		Nest creates a default ConsoleLogger internally.
		The service uses Logger, which automatically delegates to that default logger.
		
		import { Logger } from '@nestjs/common';
		private readonly logger = new Logger(AppService.name);				manual creation. Still delegates to Nest's shared global logger configured via NestFactory
		this.logger.log('Hello called');
	
	
	custom injected logger instance	that implements LoggerService
		
		import { ConsoleLogger } from '@nestjs/common';
		constructor(private readonly logger: ConsoleLogger) {}				dependency injection. Can register globally or per module
		this.logger.log('Custom log from MyLogger');


Why You Might Want a Unique (Transient) Logger Instance

1. Automatic Context Isolation
	If you give each module or service its own instance, that logger can automatically set and remember its context (the class/module name).
	ConsoleLogger.setContext
	
2. Module-level configuration
	Each instance can hold metadata or configuration specific to its module or service.
	
3. Better Debugging and Tracing
	With transient loggers, you can easily inject a new one for a specific request, job, or module

Middleware
----------
Middleware is a function which is called before the route handler. 
Middleware functions have access to the request and response objects
execute any code.
make changes to the request and the response objects.
end the request-response cycle.
call the next middleware function in the stack.
You implement custom Nest middleware in either a function, or in a class with an @Injectable() decorator
There is no place for middleware in the @Module() decorator

NestJS Lifecycle
================
1. Middleware
Runs before the request hits a controller.
Framework-level, not NestJS-specific (they’re like Express/Fastify middleware).
Good for: logging, CORS, request body parsing, authentication checks.
Can modify request/response objects directly.
Analogy: security guard at the building entrance.


2. Pipes
Run after route selection but before the controller method executes.
Work on method arguments (e.g. @Body(), @Param()).
Responsible for validation and transformation.
Analogy: the receptionist checking your paperwork is correct before letting you in.


3. Exception Filters
Run when an exception is thrown anywhere in the request/response cycle.
Catch errors and shape the outgoing error response.
Analogy: the customer service desk that handles problems.


4. Interceptors
Run before and after the controller method is called.
Can:
Transform the incoming request (like middleware, but Nest-specific).
Transform the outgoing response.
Add logic around method execution (e.g. timing, logging).
Implement cross-cutting concerns (caching, serialization, metrics, etc.).
Analogy: a tour guide who not only introduces you at the start but also gives feedback and wraps things up at the end.


Why interceptors are needed
Because none of the other three cover the “around” case:

Middleware → only before controller.
Pipes → only before controller, and only at the argument level.
Filters → only when an error occurs.
Interceptors → before and after controller, always.
This makes interceptors ideal for:
Logging & performance profiling (time a request took).
Response transformation (e.g., hide sensitive fields).
Response mapping (like converting entities into DTOs automatically).
Caching results (skip controller execution if response is already cached).

interceptors can be controller-scoped, method-scoped, or global-scoped.
