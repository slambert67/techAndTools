Step-by-step explanation

Middleware

Runs first, before NestJS handles the request.

Think: "pre-processing, logging, body parsing, authentication checks that happen outside NestJS guards."

Can modify req/res.

Guards
	Run after middleware, before the route handler.
	Responsible for authorization or permission checks.
	Return true/false (or throw ForbiddenException).

Pipes
	Run after guards, before route handler.
	Transform and validate input (e.g., DTO validation with class-validator).

Interceptors (before)
	Run before and after the route handler.
	Can modify request or response, implement caching, logging, or timeouts.
	Wraps the route handler with an observable (RxJS next.handle()).

Route handler
	

Interceptors (after)
	

Exception filters
	Run if an exception is thrown in any of the above stages.
	Can catch and handle errors globally or per-route.

| Stage               | Executes When                       |
| ------------------- | ----------------------------------- |
| Middleware          | Before Nest handles request         |
| Guards              | Before route handler                |
| Pipes               | Before route handler (after guards) |
| Interceptors (pre)  | Before route handler                |
| Route handler       | Your controller method executes     |
| Interceptors (post) | After route handler                 |
| Exception filters   | If any exception is thrown          |


Key Notes

Middleware is outside NestJS context, so it cannot inject services with DI.
Guards and Pipes can be route, controller, or global.
Interceptors wrap the route handler completely.
Exception filters only run if something throws an exception.

Middleware
==========
Runs before the request hits a controller.
Framework-level, not NestJS-specific (they’re like Express/Fastify middleware).
Good for: logging, CORS, request body parsing, authentication checks.
Can modify request/response objects directly.
Analogy: security guard at the building entrance.

There is no place for middleware in the @Module() decorator. Instead, we set them up using the configure() method of the module class

NestJS specific middleware
@Module({
  imports: [CatsModule],
})
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {					// can be made asynchronous
    consumer
      .apply(LoggerMiddleware, AnotherMiddleware)
      .forRoutes({ path: 'cats', method: RequestMethod.GET });
  }
}


@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    console.log('Request...');
    next();
  }
}

Custom Exception Filters
------------------------

import { ExceptionFilter, Catch, ArgumentsHost, HttpException } from '@nestjs/common';
import { Request, Response } from 'express';

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    const request = ctx.getRequest<Request>();
    const status = exception.getStatus();

    response
      .status(status)
      .json({
        statusCode: status,
        timestamp: new Date().toISOString(),
        path: request.url,
      });
  }
}



@Post()
@UseFilters(new HttpExceptionFilter())
async create(@Body() createCatDto: CreateCatDto) {
  throw new ForbiddenException();
}

Why interceptors are needed
Because none of the other three cover the “around” case:

Middleware → only before controller.
Pipes → only before controller, and only at the argument level.
Filters → only when an error occurs.
Interceptors → before and after controller, always.
This makes interceptors ideal for:
Logging & performance profiling (time a request took).
Response transformation (e.g., hide sensitive fields).
Response mapping (like converting entities into DTOs automatically).
Caching results (skip controller execution if response is already cached).

forRoot()
=========
ConfigModule.forRoot({ /* options */ })
	initialising ConfigModule
		reads .env files
		loads configuration sources
		sets up ConfigService
		
	But by default, the ConfigModule (and its ConfigService) is only available to the module that imported it.
	So if you have multiple feature modules or microservices, they won’t automatically see it unless you:
		Import ConfigModule in each module again, or
		Make it global. isGlobal:true
		
So why does forRoot() even exist if we can make it global?
Because forRoot() serves two separate roles
	Bootstrapping — loading environment variables and configuration.
	Registering the module (optionally globally).

new config notes
----------------
process.env is a global object containing all environment variables loaded into the process’s runtime environment.
NestJS (via @nestjs/config) doesn’t magically populate it — something has to load those .env files before or during app bootstrap.
In a monorepo with multiple microservices, each microservice runs in its own Node.js process — so each one can have its own .env file that gets loaded independently.
	so each has it's own process.env

2 options for loading .env but this option recommended
import { ConfigModule } from '@nestjs/config';
import configuration from '@myorg/common/config/configuration'; // optional shared loader

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      envFilePath: ['.env', '.env.local'], // can be absolute or relative
      load: [configuration],
    }),
  ],
})
export class AppModule {}

NestJS internally uses dotenv to read the .env files listed in envFilePath.
Each key/value pair in that file is loaded into process.env.
Then those values are also available via ConfigService.


First Principles: What ConfigModule.forRoot() actually does
NestJS:
	Loads .env files (via dotenv)
	Populates process.env
	Registers a global ConfigService
	Makes the loaded values available to all providers in that same process
	So you only need to call .forRoot() once per Node.js process.
	All other modules can simply import ConfigModule (without .forRoot()).

Option B — Each app calls .forRoot(), using shared config factory

This is the most flexible and enterprise-safe approach for a true multi-app monorepo.


What load: [configuration] Does

When you initialize the ConfigModule in NestJS like this:

ConfigModule.forRoot({
  isGlobal: true,
  envFilePath: ['.env'],
  load: [configuration],
});


The load property expects one or more factory functions that return an object.
These functions are called configuration loaders, and they let you define your app’s configuration structure in code.

So:

load: [configuration]


means:

“Run the function called configuration, get an object from it, and merge that into the config system alongside the .env variables.”

⚙️ Example: configuration.ts

Let’s say you create this file in a shared library, like:

libs/common/src/config/configuration.ts

export default () => ({
  app: {
    name: process.env.APP_NAME || 'My App',
    port: parseInt(process.env.PORT ?? '3000', 10),
  },
  database: {
    url: process.env.DATABASE_URL,
  },
  rabbitmq: {
    url: process.env.RABBITMQ_URL,
  },
});


This function:

Reads raw values from process.env

Organizes them into a structured object

Optionally casts types (like parseInt for numbers)

🧠 Why use this instead of process.env everywhere?

Because it gives you:

Centralized config (everything in one predictable place)

Type safety and autocompletion (if you define types)

Environment abstraction — you can merge .env values, defaults, and computed logic

Reusable config across apps (share this loader in your monorepo)

So instead of this scattered pattern:

const port = parseInt(process.env.PORT ?? '3000', 10);


You can do this anywhere:

const port = configService.get<number>('app.port');


Same value, but now:

It’s type-safe.

It comes from a validated, normalized config tree.

You can share the same config logic across services.


TL;DR

Shared loader → only common config (NODE_ENV, logging, maybe API version)

Service-specific loader → each microservice loads its own keys and structure

Combine them in ConfigModule.forRoot({ load: [shared, serviceSpecific] })

Typed with registerAs → keeps type safety without forcing every service to have identical config

monorepo/multiple microservices
	Put ConfigModule.forRoot() once in a shared Core or Common library that all apps can import,
	and NOT inside each microservice’s module directly.
	e.g. libs/common/src/config/[config.module.ts, config.service.ts, configuration.ts]

DTOs
====
| Purpose               | Description                                                                          |
| --------------------- | ------------------------------------------------------------------------------------ |
| **1. Validation**     | Ensure incoming data meets expectations (e.g., correct types, formats, constraints). |
| **2. Type safety**    | Leverage TypeScript to guarantee predictable structures.                             |
| **3. Transformation** | Convert plain JSON objects into typed class instances (and vice versa).              |
| **4. Decoupling**     | Separate external API contracts from internal domain models or database entities.    |


1. Request enters controller
2. NestJS automatically creates a DTO instance from JSON body
3. The ValidationPipe (if enabled) validates it using class-validator
4. If valid, it’s passed to the route handler as a typed DTO
5. If invalid, a 400 Bad Request is thrown automatically

NestJS integrates two libraries:
	class-validator → for validation decorators like @IsEmail(), @MinLength()
	class-transformer → for converting plain JSON objects to DTO class instances

Together, they allow you to:
	Validate shape and content
	Transform types automatically (e.g. strings to numbers, booleans)
	Strip out extra, unwanted properties (if configured)
	
You can (and often should) have two sets of DTOs:
	Input DTOs for data coming into the system (validation, creation, updates)
	Output DTOs for data leaving the system (response shaping, serialization)
	

DTO vs Entity vs DAO vs Model
| Layer                | Purpose                                         | Example                            |
| -------------------- | ----------------------------------------------- | ---------------------------------- |
| **DTO**              | Defines data shape at boundaries (input/output) | `CreateUserDto`, `UserResponseDto` |
| **Entity**           | Represents a database table (ORM layer)         | `UserEntity` (TypeORM, Prisma)     |
| **DAO / Repository** | Performs persistence logic                      | `UserDao`                          |
| **Service**          | Business logic                                  | `UserService`                      |



Best Practices

✅ 1. Always use classes (not interfaces)
Interfaces are erased at runtime, but classes allow runtime validation and transformation.

✅ 2. Keep DTOs flat and simple
They should mirror request/response structure, not complex domain logic.

✅ 3. Use separate DTOs for input and output
This prevents leaking sensitive data and makes versioning easier.

✅ 4. Leverage validation decorators liberally
They’re cheap, declarative, and protect your endpoints.

✅ 5. Use whitelist: true in production
Strips out unexpected data and helps mitigate injection attacks.

✅ 6. Use PartialType and OmitType
NestJS provides helpers to avoid repeating DTO fields.

Example:

import { PartialType } from '@nestjs/mapped-types';
export class UpdateUserDto extends PartialType(CreateUserDto) {}


This automatically makes all fields optional — perfect for PATCH endpoints.


[Client]
   ↓ sends HTTP POST /users
[Controller]
   ↓ (ValidationPipe)
CreateUserDto ← validates request shape & data
   ↓
[Service]
   ↓
[DAO / Repository]
   ↓
[Database]
   ↓
Entity → transformed to Output DTO
   ↓
[Controller returns]
UserResponseDto → sent to client


| Aspect           | Description                                                          |
| ---------------- | -------------------------------------------------------------------- |
| **What**         | DTO = Data Transfer Object, defines shape of data in/out of your app |
| **Used for**     | Validation, transformation, typing, and decoupling                   |
| **Common tools** | `class-validator`, `class-transformer`, `ValidationPipe`             |
| **Where**        | Controllers (HTTP, WS, GraphQL, microservices)                       |
| **Why**          | Security, maintainability, readability, testability                  |
| **Output DTOs**  | Prevent exposing sensitive or internal data                          |
| **Helpers**      | `PartialType`, `OmitType`, `PickType` for reuse                      |

Best Practices
✅ Use @nestjs/cli monorepo mode for automatic build support.
✅ Keep apps small; move shared logic into libs/.
✅ Make DTOs the single source of truth for inter-service contracts.
✅ Use YAML + ConfigModule for consistent config across all apps.
✅ Keep transport adapters (RabbitMQ, Kafka, Redis) inside libs/infra.
✅ Use tsconfig path aliases (@libs/...) to simplify imports.
✅ Avoid direct cross-app imports. Communicate through queues, not code.
✅ Add lint rules (e.g. Nx or ESLint project boundaries) to enforce separation.
